# T12 review/evidence plan — Level 1–100 progression architecture

**Preparation-only artifact.** This document predefines the evidence T12 must capture after legal activation. It does not score T12 and does not substitute for independent critic execution.

## Required critics

T12 requires C2, C3, C4, C6 and C7. Each applicable mandatory dimension must be strictly greater than 9.0 unrounded, target 10/10, with zero unresolved mandatory defects. Builder self-review is not an independent critic.

## Exact-source evidence bundle

The T12 candidate review packet must contain:

- exact post-T11 integration base and exact T12 candidate commit;
- authorized changed-file manifest proving only `@reservation:T12` plus approved integration-owner changes;
- hashes of `progression_levels_v1.json`, `progression_milestones_v1.json`, upstream binding record and validator version;
- exact accepted T07/T08 integrated sources and accepted T10/T11 completion/integration sources;
- static validation output for the exact shipping progression data;
- impacted regression output for approved T01–T11;
- performance/query telemetry from the exact candidate;
- raw independent critic inputs/outputs and defect dispositions.

## Mandatory static reports

1. **100-level completeness report** — exactly one record for every integer Level 1–100, unique stable IDs, deterministic ordering.
2. **Prerequisite DAG report** — no missing target, self-loop, cycle, unreachable level or impossible mandatory chain.
3. **Practical-progression coverage** — every level has at least one meaningful progression effect/unlock; no counter-only filler.
4. **Visible-progression cadence** — declared visible hooks satisfy the frozen cadence with no unsupported gap beyond the accepted contract.
5. **Major-milestone cadence** — each default ten-level boundary has a major milestone or an explicit accepted same-band exception record.
6. **Spend-blind audit** — no purchase history, VIP, premium spend, payer status, premium-currency spend or energy-wall eligibility input.
7. **Stable-ID audit** — unique level/milestone/event IDs and no provisional T10/T11 ID in shipping data.
8. **Upstream authority audit** — T12 reads approved T07/T08/T10/T11 state through published interfaces and does not grant/debit inventory, commit transforms, spawn camp content or alter T13 difficulty.
9. **One-time/idempotency report** — replayed evaluation cannot duplicate one-time progression events or skip prerequisites.
10. **Later-owner boundary report** — no T13/T14/T33+/T44–T52 implementation was pulled into T12.

## Functional evidence sequences

### Sequence A — ordinary level progression

Capture an exact candidate sequence showing:

1. current level not yet eligible;
2. last missing accepted prerequisite becomes true;
3. T12 reports eligibility without mutating upstream systems;
4. integration commits the actual upstream action through the proper owner where applicable;
5. T12 advances exactly once;
6. repeated/replayed evaluation produces no duplicate unlock/event.

### Sequence B — visible progression hook

Use a level whose record declares a visible progression requirement:

- before state;
- eligible state and next-objective readability;
- accepted T10/T11 or later-owner visible change triggered through the owner system;
- complete state from gameplay scale and at least one detail/three-quarter view;
- replay attempt proving no duplicate visible state/event.

T12 itself must not fake later-owner content simply to satisfy this sequence.

### Sequence C — major milestone

For at least one ten-level boundary and the Level 100 terminal milestone:

- prerequisite closure;
- major milestone eligibility;
- major milestone completion;
- next-band/terminal state;
- stable event identity and replay protection.

## Adaptive/readability evidence

Where T12 adds player-facing progression presentation, capture the same exact candidate on:

- phone landscape;
- tablet landscape;
- foldable supported landscape state;
- native 3840×2160 scale-1 development evidence where the pipeline supports it.

The evidence must show current level, next meaningful objective/unlock and milestone state without obscuring joystick, contextual action, actor, target or world-response readability. This is not T68/T69 physical-device certification.

## C2 — Technical / Visual Integrity

Mandatory review focus:

- no duplicated/contradictory level or event state;
- transition/result presentation matches actual authoritative progression state;
- no stale objective after level completion;
- no provisional/missing upstream ID in shipping data;
- no cross-view contradiction where player-facing progression presentation exists.

## C3 — Havenline Gameplay Identity

Mandatory review focus:

- progression reinforces MOVE → AUTO-INTERACT → GATHER → CARRY → DELIVER → TRANSFORM → RESCUE → BUILD/UPGRADE → EXPLORE → DEFEND;
- no permanent action-button growth caused by progression;
- no manual inventory/skill-tree/4X-management substitution;
- no hidden-menu progression replacing physical world response;
- no energy wall or spend-linked progression eligibility.

## C4 — Gameplay UX / Readability

Mandatory review focus:

- current level and next meaningful objective are understandable;
- locked/eligible/complete milestone state is clear;
- visible world change and progression result are causally readable;
- no unexplained prerequisite or dead-end state;
- adaptive layouts remain uncluttered.

## C6 — Performance

Record at minimum:

- load/parse/validation time for the 100-level datasets;
- common current-level/next-objective query cost;
- milestone/prerequisite query cost;
- repeated-evaluation allocation/object growth;
- event/history bounds;
- proof unchanged state does not trigger full-world or full-graph rebuild every frame;
- impacted integrated scene telemetry after T12 is wired.

Early software/CI measurements protect headroom but do not certify final physical native-4K/60 performance.

## C7 — Progression / Difficulty

T12 review focus is progression architecture, not T13 adaptive tuning:

- meaningful progression at every level;
- no long boring stretches or empty filler levels;
- visible improvement cadence remains useful and readable;
- major milestones feel structurally meaningful;
- no impossible progression chain;
- no HP-only/stat-only substitute where a visible/system progression effect is required;
- clean bounded interface for T13 to add spend-blind adaptive challenge later without rewriting T12 topology.

## Mandatory defect rules

Any of the following blocks approval regardless of average score:

- missing/unreachable shipping level;
- duplicate stable ID or one-time event;
- prerequisite cycle/dead end;
- spend/VIP/energy-gated level eligibility;
- provisional T10/T11 ID shipped without activation reconciliation;
- direct T12 mutation of inventory, transform transaction state or camp content;
- unresolved visual-progression cadence failure;
- unresolved mandatory critic score at or below 9.0;
- stale/missing exact-source evidence.
