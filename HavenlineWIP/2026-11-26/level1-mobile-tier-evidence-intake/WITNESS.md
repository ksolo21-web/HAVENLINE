## What actually exists
Exact integrated source at [11c14a1c](https://github.com/ksolo21-web/HAVENLINE/blob/11c14a1c41971067c7dc97db69375f720a408f68/HavenlineLevel1/previews/integrated_opening.gd) selects the integrated scene separately from legacy F5. Its project declares Compatibility; the authorized minimum repeatable visual control was 1280×720 X11 software llvmpipe, ortho 13, fixed-step test harness, 6 true native captures and 57 writer +10 cold checks on **11c with detached paid-pine patch**, not a pristine retail release. The visible stock frame shows the 10×8 m camp, old placeholder walls/gates, small character, central hearth and snow. Shadowed faces are nearly black. This is a baseline to identify regressions, not the approved art floor, not a phone, and not evidence that stock UI/rig/primitive art pass. Exact checked scripts show fixed directional rotation/shadows but no explicit exposure, environment or tonemap override. Native pixel stats are descriptive whole-frame data; white snow, black HUD/shadow, and real-device display HDR cannot be inferred from them.

Read-only source inventory found stock Character1 with 66 joints, 96,001 authored triangles, and three 4096² texture sources (192 MiB nominal RGBA8 base-level bytes before mips; not active GPU memory). The wire-format JPGs don't determine runtime material residency. 856,696 authored hearth tris and three 2048² maps, 84,041 pad tris and 2048²/1024² maps are sealed hydrated inputs; their authored counts are not stock frame draw counters or per-device peaks. Six exterior pine instances use the three exact 9,576-tri source variants and much smaller images (up to 128×192). Confirm real importer/LOD/visibility and runtime memory before targeting the highest counts. Preserve all sources and separate clean Character1 rig decisions.

## One witness per physical device, actual tier, display mode, and APK
Start on one available representative **medium Android phone** with only existing build settings: bracket the median path before any tier tuning. On the same device, once three immutable tier configurations *exist and are authorized*, compare Ultra, High and Low one at a time using the same device/OS build, actual ref scene+asset/camera SHA, preserve scale, retain exact touch input and UI/HUD composition, alternate tier order with cooled devices. A second GPU/driver is an independent witness, not a substitute for the medium-phone result. High/Low evidence transports nowhere: differentiated render buffers/tier and actual refresh must be observed per device. Ultra high-end 4K/60–120 remains a stated ambition, not a setting or result. Verify 4K refers to native internal game resolution (not display mode, export still, upscale or dynamic maximum); verify actual 60/120 presented cadence separately from configured display refresh. Record native lower viewport when a device doesn't support that mode. Don't disable system thermal safety or use clock-lock in shipping approval runs.

Record APK SHA/version, exact scene+scripts+assets+settings SHA, package layer on surface, engine and graphics API/vendor/GPU driver; monitor requested refresh and actual app/presented cadence; distinguish native render size, composited surface size, display mode, down/upscale and dynamic resolution samples; store device model/SoC/RAM class, Android/driver release, screen brightness, thermal start/end, charging/network status. Use a marked disposable app profile with no owner saves. No source changes are part of this plan. Capture screenshots without recording overhead in separate identical state passes. Any intrusive profiler attached to release build gets a separate overhead baseline and must not be conflated with untouched presentation pacing.
